## Workspace and Interaction Contract

### Page structure

Render a single captain-only **Week setup** workspace for the authenticated identity's assigned, pre-provisioned week. It is a one-column sequence of panels, never a calendar grid or dense table:

1. Context header: `Week {n}`, derived date range, `Atlantic/Madeira`, assigned captain identity, and a status chip: `Draft`, `Setup published — intake closed`, or `Changes ready to publish`.
2. **Week details** panel: required theme and public description.
3. **Activities** panel: Tuesday talks then Wednesday workshops, each with an ordered card stack.
4. **Proposal form** panel: ordered field-card stack.
5. **Demo Day timing** panel.
6. **Readiness** panel followed by preview and publish actions.

The `Week {n}` display heading and the final readiness/publish area are the two visual anchors. The readiness state receives stronger structural emphasis than individual editor panels so the captain can immediately see what blocks publication.

Do not render a freely-create-week control. If the active Nostr identity is not assigned to a provisioned week, render a non-editable access panel: `This identity is not assigned a week to configure.` Do not expose editor or publish controls. This is an interface cue only; authorization must remain enforced outside the interface.

The initial editor state is a local draft. Input changes never show a success message implying publication. Show a compact `Changes saved locally` status only after the draft has changed. First publication is possible only through **Create week**; later publication is possible only through **Publish changes**. Both actions are disabled until readiness is complete and show a busy state while signing/publishing. Successful publication shows: `Week published. Intake remains closed.`

### Week details

- Use one required single-line `Theme` input and one required `Public description` textarea. Show `Atlantic/Madeira` as read-only scheduling context, not an editable timezone picker.
- Place required markers in the visible label and attach help/error text to its field with `aria-describedby`.
- Validate on blur and on an attempted create/publish. Retain entered values and focus the first invalid control after a blocked submission.

### Activities

- Seed separate Tuesday-talk and Wednesday-workshop groups from the editable templates. Each group has an **Add activity** button placed after its card stack.
- Render each activity as a bordered, ordered, collapsible card—not a row in a calendar. Its closed header shows ordinal, title, date, start–end time, and location. A newly added or invalid card is expanded; valid existing cards are closed by default.
- The expanded card contains required title, date, start time, end time, and location inputs, plus an optional link input. Help text reads: `Times use Atlantic/Madeira.`
- Give every card visible text controls: **Move earlier**, **Move later**, **Remove activity**, and an expand/collapse button whose `aria-expanded` reflects state. Disable Move earlier on the first card and Move later on the last. Native buttons, not drag and drop, are the required reorder method.
- After a move, preserve focus on the moved card's corresponding movement control and announce its new ordinal through the existing polite notice/live region pattern.
- An empty day group renders its documented empty state, retains the group heading, and offers **Add activity**. Its other controls remain absent.

### Proposal form

- Render field definitions as ordered, collapsible cards using the same movement contract as activities. Each expanded card has required `Field label`, a `Required for proposals` checkbox, and visible **Move earlier**, **Move later**, and **Remove field** controls.
- Stable field identity is never displayed as editable UI and must not be regenerated by rename or reorder. The editor treats label/order as presentation changes only.
- If no fields remain, render the documented empty state and **Add field** action. Publishing stays blocked until the minimum valid form schema defined by the domain validator is restored.

### Demo Day timing

- Render two required whole-minute numeric inputs: `Presentation duration` and `Question duration`. Their minimum is 1 minute; zero, decimals, and negative values are invalid.
- Seed `6` and `2` respectively. Show a derived, read-only summary immediately below: `Demo Day timing: 6:00 presentation + 2:00 questions.` Update it from valid draft values; `1` and `2` must read `1:00 presentation + 2:00 questions.`

### Readiness, preview, and publication

- The readiness panel is visible at all times and lists Week details, Tuesday activities, Wednesday activities, Proposal form, and Demo Day timing. Each item is either `Ready` or `Needs attention`; clicking a non-ready item expands its panel/card and moves focus to the first invalid field.
- **Preview week** changes the entire workspace to the exact public-facing configuration view and replaces all editing controls with **Return to editing**. In preview, display only the theme, public description, dated agenda, locations/links, Demo Day timing, and proposal-field labels with required markers. Do not display draft/readiness data, captain controls, whitelisted participants, local status, or a proposal-submission action; intake is closed in this phase.
- Do not let preview bypass validation or publication. Returning to editing restores the same local draft and expanded-card state.
- When fields are valid, surface the primary action at the end of the readiness panel. It remains visually distinct from secondary Preview and Return actions. Any relay/signing failure keeps the draft intact and presents the documented error notice with retry.

### Responsive and accessibility behavior

- At widths below 660px, retain source order; panels remain one column and all action rows become full-width stacked buttons. Never rely on horizontal scrolling for fields, readiness items, or card controls.
- Use native `<button>`, `<input>`, `<textarea>`, `<select>` only where applicable, headings in hierarchical order, `<section>`/`<fieldset>` grouping, programmatic labels, and the existing `:focus-visible` cyan ring. Icon-only controls are not permitted for new Phase 1 operations.
- Dynamic titles, descriptions, locations, links, field labels, and validation/error text must pass through `escapeHtml`/`escapeAttr`; render external links with a safe validated URL and descriptive text.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Card status-marker and inline icon gap |
| sm | 8px | Label/help and compact control gaps |
| md | 16px | Default field and card-internal spacing |
| lg | 24px | Panel padding and card-stack separation |
| xl | 32px | Major workspace section gaps |
| 2xl | 48px | Page-to-workspace separation |
| 3xl | 64px | Page-level vertical separation on large screens |

Exceptions: 44px minimum hit area for every interactive control, including compact movement controls; this is an accessibility floor, not a spacing token.

## Typography

Use exactly these four text sizes for new Phase 1 UI, retaining only the two declared weights:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body and input | 16px | 400 | 1.5 |
| Label, helper, status | 14px | 700 | 1.4 |
| Section heading | 22px | 700 | 1.2 |
| Week display heading | 48px | 700 | 1.1 |

Labels, status chips, and buttons may remain uppercase to match the existing shell, but text must not rely on color or uppercase alone to express state.

## Color

Preserve the existing CSS semantic tokens and their light-mode equivalents. The percentage split describes the Phase 1 workspace composition, not a hard-coded new palette.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--paper` / `#05070d` dark; `#f3f7fa` light | Page background and negative space |
| Secondary (30%) | `--surface` / `#0a101c` dark; `#ffffff` light | Setup panels, agenda cards, form cards, readiness panel |
| Accent (10%) | `--accent` / `#61e9ff` dark; `#087f9f` light | Primary Create/Publish action, visible keyboard focus, selected preview mode, active card/readiness marker |
| Destructive | `--red` / `#ff597d` dark; `#a52d49` light | Remove activity/field controls, destructive confirmations, destructive error treatment only |

Accent reserved for: **Create week**, **Publish changes**, focus outlines, selected Preview state, and the active/ready structural marker. Secondary actions, ordinary links, movement controls, and descriptive status must use neutral or semantic tokens instead.

## UI Considerations

> Shape-rooted UI state coverage for the Phase 1 editor. Empty/error copy is defined above and referenced here rather than duplicated.

Applicable state considerations resolved: 12 covered, 0 backstop, 0 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | Tuesday and Wednesday activity collections | ✅ covered | An empty day retains its heading, renders the documented activity empty-state copy, and exposes only **Add activity**. |
| loading | Assigned week/public configuration | ✅ covered | Before initial configuration resolution, render a non-editable panel with the existing spinner and `Loading week configuration…`; do not show stale publish controls. |
| error | Initial configuration load and signing/publish | ✅ covered | Load failure renders a retry action; publish failure uses the documented error notice, preserves the local draft, and provides **Try again**. |
| populated | Activity collections and proposal field collection | ✅ covered | Ordered collapsible cards show day grouping, summary metadata, and explicit movement/edit/remove controls at typical and larger volumes. |
| partial | Week details, activity cards, proposal field cards, timing form | ✅ covered | Invalid/incomplete fields retain entered data, show inline errors, mark the readiness item `Needs attention`, and block Create/Publish. |
| overflow | Activity and proposal field collections | ✅ covered | Card stacks grow vertically; no horizontal scroll, clipping, or dense-table fallback is permitted. |
| zero-one-many | Activity and proposal field collections | ✅ covered | Zero uses the documented empty state; one renders its ordinal and disabled boundary move controls; many retain ordered cards with first/last movement boundaries. |
| long-text | Theme, public description, activity titles/locations, proposal field labels, notices | ✅ covered | Inputs and textareas wrap without data loss; card summaries and status chips use `overflow-wrap:anywhere`; compact header chips may ellipsize only the identity name while keeping its full accessible name. |
| empty | Proposal form | ✅ covered | The documented proposal-form empty state shows **Add field** and keeps publication blocked until the domain-valid schema exists. |
| loading | Preview mode | ✅ covered | If a public configuration must be resolved for preview, disable the toggle, show `Loading preview…`, then replace editor controls atomically with the public view. |
| error | Authorization boundary | ✅ covered | An unassigned identity gets the documented access panel with no editable or publication controls; server/domain authorization remains authoritative. |
| long-text | Interactive controls and navigation | ✅ covered | New control labels are fixed short strings; dynamic labels are placed in wrapping card content rather than movement/remove buttons. |
